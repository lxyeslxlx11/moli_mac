byte2=1/3 的全部27,785条记录，payload u32le@12 等于索引长度。byte2=0/2 的全部69条记录则均不相等。因此不能用同一条 `header@12 == index.length` 规则校验四种记录。

byte3 在样本中取值广泛，未发现足以指定语义的证据。不得假设为固定0或仅允许当前少数取值。

索引标识也不是全表唯一：Joy 有457个标识值出现不止一次，V3 有8个；记录序号与标识须分别保存，查找不能假定 `id == ordinal` 或构建唯一字典时静默覆盖。

## 事实：byte2=0 的原始布局

仅V3含4条，全部满足 `index.length = 16 + width × height`。对应索引序号为380/381/402/403，尺寸分别4×3、4×4、4×3、4×4。

这4条的 `u32le@12 − width×height` 均为8,625,956。该字段语义未知；形似写入时遗留的地址/偏移值只是推测，不能当作规范，也不应硬编码该常量。

可实现保守的读取：按索引边界读入记录，校验RD/version0、头与索引维度相等、精确长度，再将剩余 `width×height` 字节作为未解释的索引值。由于只有4条、且尺寸都很小，不能外推到所有历史版本。

## 事实：byte2=2 的原始布局

`index.length = 20 + width × height + u32le@16`

## 推测与待验证：颜色、透明和空间方向

- “每字节为一个调色板索引、尾部每3字节为一个颜色”得到长度及索引范围关系支持，是强结构推测；尚未用官方渲染行为验证。
- RGB/BGR顺序、色彩空间、各byte的意义、调色板第一项是否透明均未证实。此检查不能在这两种通道排列中作选择。
- Joy version2中2条、V3 version2中11条候选像素全为0，但其第一组三字节颜色值并不相同。这与“0是透明键”假说相容，不能证明它；也不能把调色板第一项强制当固定黑色。
- version2里部分大尺寸记录没有0像素，说明不能从“没有透明零”推断像素数据损坏。
- 存储顺序是从顶到下还是从底到上、实际坐标原点和行间对齐语义未证实。全样本宽度都是4的倍数，不能据此证明非4对齐宽度的文件不存在，也不能直接把宽度字段当作未填充的内容宽度。
- byte2=3共有6,166条，其u32le@16全落在6至768且被3整除。这支持扩展头含调色板长度的猜测；RLE内容检查由父分析任务进行，本次独立复核没有宣称version3解码成功。

## 建议解析器边界

首个最小可靠实现可支持version0/2，仅输出候选像素索引及调色板字节，UI将图像标为“索引值灰度预览”。颜色模式和翻转方向应显式标为实验选项，不能宣称官方颜色/透明还原。

结构读取需拒绝：头部不足16/20字节、magic错误、不支持的version、索引越界、尺寸为0或超过资源预算、乘加溢出、头/索引维度不一致、长度不精确、version2调色板长度为0/非3倍数/超过预算、任何候选像素索引超出实际调色板项数。

不要拒绝：原始version0/2的header@12不等于记录长度、合法短调色板、重复ID、样本中的全部0像素。byte3与header@12语义未明，保存其原值供诊断即可，不用于跟随指针或任意内存操作。

本次静态检查通过；没有执行GUI、输出官方图片、验证真实颜色或空间方向。没有遇到环境权限阻断。
